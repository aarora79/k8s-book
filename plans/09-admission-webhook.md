# Plan: chapter 9, an admission webhook

Folder: `chapters/09-admission-webhook/`. Standard library plus `k8s.io/api/admission/v1` types.

## Goal

The reader adds their own check to every write the API server accepts, first as webhooks, then as in-process CEL policies, and compares the two.

## Verified facts (2026-11-16)

- ValidatingAdmissionPolicy is GA since Kubernetes 1.30.
- MutatingAdmissionPolicy was beta in 1.34; one source reports GA in 1.36. Check its status in 1.37 and whether kind enables it by default. If GA, include it as step 5; if not, keep it in "Improving and expanding".

## Design decisions

- The webhook runs as a Deployment in namespace `ch09` behind a Service, with a self-signed CA generated by a script (Go `crypto/x509`, no openssl dependency). The CA bundle goes into the webhook configuration's `caBundle`.
- Scope the webhooks to namespaces labeled `hmlk8s/admission=on` so a broken webhook cannot lock up the cluster. `failurePolicy: Fail`, `sideEffects: None`, `timeoutSeconds: 5`.
- The policy: reject pods with any container lacking `resources.limits.memory`, or with an image outside an allowed registry list (`docker.io/library/` and `registry.k8s.io/` by default). This is the same rule chapter 11 turns on for MCP Gateway Registry, so make the registry list configurable.

## Steps

1. **step1: allow everything, log everything.** An HTTPS server that decodes `AdmissionReview`, logs kind, namespace, name, operation and user, and allows. Register it and create a pod to see the request.
2. **step2: validate.** Reject per the policy, with a message that names the container and the missing field.
3. **step3: mutate.** A second endpoint returning a base64 JSON patch that adds `hmlk8s/admitted-by: webhook` and a default `app` label when missing.
4. **step4: the same rule in CEL.** A ValidatingAdmissionPolicy and binding with the same checks, bound to the same namespace label. Compare messages and latency (time 20 pod creates each way).
5. **step5: MutatingAdmissionPolicy (if GA in 1.37).** The step 3 mutation in CEL.

## Tests

- A pod without limits is rejected in a labeled namespace and admitted in an unlabeled one.
- A pod from an unapproved registry is rejected with the right message.
- A compliant pod gets the added label.
- The CEL policy rejects the same bad pods with the webhook removed.
- With the webhook scaled to zero and `failurePolicy: Fail`, pod creation in the labeled namespace fails; in other namespaces it works.
